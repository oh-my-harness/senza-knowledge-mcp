# 领域知识库 · 一阶段设计（MCP 优先 + 管理后台）

> 背景：公司采用全息光刻等前沿技术路线，通用模型缺乏实现级领域知识（HoloLithoSim 实证报告结论）。需要一个团队共享的「领域知识库」：沉淀领域文档与知识、供 coding agent 在开发时随时检索与写回，消除「每会话重复交代领域知识」的知识税。
>
> 定位：核心逻辑与接口形态**解耦**。一阶段为本地单机 MCP 服务 + 管理后台，二阶段把同一套知识核心迁到云端（MCP 接口原样保留），不推倒重来。
>
> **接口决策**：知识库的主接口是 **MCP 服务**（面向 coding agent，因为研发主力消费方是 coding agent），管理后台负责文档入库与人工治理，两者职责分离。

---

## 一、目标与边界

### 目标
- 单机运行的**知识库 MCP 服务**：coding agent（senza-coder、外部 Claude Code 等）通过 MCP 检索 / 读取 / 写回知识库。
- 适配 Senza 多模态：知识库能存文档与图片，图片在使用时由多模态模型理解。
- 支持文档搜集与入库（MinerU 解析 → 原始层 → 索引）。
- 支持 llm-wiki：agent 把对拍教训 / 正确方案增量写回知识层。
- 核心逻辑与 Folumi 形态解耦，成为可复用的「知识库核心」，二阶段直接迁云端。

### 边界
- 一阶段单机、单用户（二阶段才做多用户权限）。
- 复用 Folumi 已验证的 RAG / 知识源实现范本，不重造轮子。
- MinerU 作为**外部进程/服务**通过 CLI/HTTP 调用（GPL-3.0 隔离），不链接进底座。

## 二、数据分层（持久层，核心架构）

```
┌─ 原始层（不可变 · 权威）───────────────────────────┐
│  文档（文本/Markdown） 或 文档+图片                    │
│  来源：MinerU 解析产物 / 管理后台投入的文本            │
│  规则：原样存储，永不改动                              │
└────────────────────────────────────────────────────┘
              ↑ 原始为依据（可重建一切派生）
┌─ 关联层（派生 · 可重建）───────────────────────────┐
│  ① 关联索引：知识页/概念之间的显式关系                │
│     由 heartbeat agent 定时自动整理                  │
│  ② 归纳知识页（带 human-on-the-loop）：              │
│     从散文档归纳出的结构化领域知识总表                │
└────────────────────────────────────────────────────┘
```

- **原始层唯一权威**，关联层可由原始层重建（继承 Folumi「原始权威、索引可重建」原则）。
- **图片不预嵌入语义**：原始层存文档+图片，图片在「使用时」由多模态模型按需理解，避免「入库时理解一次、理解过期」。
- **关联层由 heartbeat agent 维护**：定时扫描原始层 → 发现关联/归纳 → 写回关联层，增量、可审计。
- 关联索引（低风险，先做）与 归纳知识页（需写权限、human-on-the-loop，独立能力）**拆开**。

## 三、系统形态（MCP 优先 + 管理后台）

```
  coding agent（MCP 客户端）
  ├─ senza-coder / mcp-coded        ┐
  └─ 外部 Claude Code 等            ┘  │ MCP 标准协议
                                        ▼
┌──────────────────────────────────────────────────────┐
│  知识库 MCP 服务（一阶段核心接口）                      │
│  ├─ tools:   search(检索) / read(读取) / upsert(写回) │
│  ├─ resources: 知识页 / 图片 / 关联                  │
│  └─ prompts:  领域 skill（自动注入，消知识税）         │
└──────────────────────────────────────────────────────┘
        │
┌──────────────────────────────────────────────────────┐
│  知识库核心（与接口解耦）                               │
│   原始层 + 关联层 + 入库管线 + 检索(LanceDB)          │
└──────────────────────────────────────────────────────┘
        │
┌──────────────────────────────────────────────────────┐
│  管理后台（FastAPI，人工治理）                         │
│   文档上传/入库 · 知识库查看 · 归纳审批(human-on-loop) │
└──────────────────────────────────────────────────────┘
```

- **MCP 服务**：主接口，供 coding agent 检索、读取、写回。`llm-harness-mcp` 全套能力在 Rust 侧；Python SDK 有 `McpManager`/`McpServerConfig`。
- **知识库核心**：原始层 + 关联层 + 入库管线 + LanceDB 检索，与接口解耦，二阶段迁云端后 MCP 接口原样保留。
- **管理后台**：文档上传/入库、查看知识库、人工审批归纳知识页（human-on-the-loop）。**不做问答主入口**——问答由 coding agent 经 MCP 完成。

### 职责分工
| 能力 | 走 MCP（agent） | 走管理后台/CLI（人工） |
|------|----------------|----------------------|
| 检索（search） | ✅ | — |
| 读取知识页/图片（read） | ✅ | ✅（浏览） |
| 写回教训/关联（upsert） | ✅ | — |
| 文档上传/入库（MinerU） | — | ✅ |
| 归纳知识页审批 | — | ✅（human-on-the-loop） |
| 知识库管理（删除/整理） | — | ✅ |

## 四、文档入库管线

```
PDF / 文本 ──► MinerU（外部服务，进程隔离）
                 │  输出 Markdown + 结构化 JSON
                 │  + 图片列表 + 图片描述 + 公式(LaTeX) + 表格(HTML)
                 ▼
            原始层存储（不可变）
              ├─ 文档（文本）
              └─ 图片（带描述侧栏）——使用时按需送多模态模型
                 │
                 ▼
            切分 → embedding → LanceDB 检索（RAG）
```

- **入口**：管理后台（文档上传）或 CLI。MinerU 为外部独立进程/服务，CLI 或 HTTP 调用（进程级隔离，规避 GPL 传染；可替换为 Dolphin / 自研解析器）。
- 产出：文档文本 + 图片 + 图片描述 + 公式/表格结构化。
- 原始层不可变；检索索引（LanceDB embedding）为派生、可重建。

## 五、组件划分（与 Folumi 形态解耦的「知识库核心」）

```
领域知识库（一阶段）
├─ MCP 服务 (mcp server)           —— search / read / upsert / skills（coding agent 主接口）
├─ 管理后台 (FastAPI)              —— 文档上传 / 知识库查看 / 归纳审批
├─ 入库管线                        —— MinerU 解析 → 原始层 → LanceDB 索引
├─ 知识库核心（解耦）
│     ├─ knowledge.local_source()  —— LanceDB 领域知识源（RAG）
│     ├─ load_skills()             —— 领域 skill 自动加载（免知识税）
│     ├─ Attachment / 多模态       —— 图片/PDF（使用时按需理解）
│     └─ 关联层维护器（heartbeat agent）
│           ├─ 关联索引（定时，低风险）
│           └─ 归纳知识页（trigger，human-on-the-loop）
└─ 整理流程                        —— 从散资料 → 结构化知识页（半自动）
```

### 关键组件说明
1. **MCP 服务**：`McpManager` / `McpServerConfig` 暴露 search/read/upsert 工具 + 领域 skill prompts。coding agent 经此检索、读取、写回。
2. **RAG**：`knowledge.local_source()`（LanceDB）检索，返回带引用依据。
3. **skill 自动加载**：`load_skills()`，把领域判据/公式/陷阱/验收标准做成薄 skill，MCP prompts 自动注入（消除知识税）。
4. **关联层**：heartbeat（`create_heartbeat_stream`）+ AgentHarness 定时整理。关联索引先行；归纳知识页 trigger + human-on-the-loop。
5. **llm-wiki 增量写回**：agent 经 MCP upsert，把「对拍教训/正确方案」写回知识页（skill / wiki 双层），增量维护。
6. **管理后台**：FastAPI。文档上传触发入库管线；归纳知识页展示 + 人工审批。

## 六、Senza Python SDK 能力确认（已实测 `.pyi`）

可直接复用（无需动 Rust）：
- `Attachment`：image_url / image_base64 / document_file（多模态）
- `knowledge.local_source()` / `knowledge.memory_*`：RAG 源 + 记忆
- `Skill` / `load_skills()`：薄技能自动加载
- `create_heartbeat_stream` / `create_timer_stream`：heartbeat agent 定时
- `Inspector`：调试
- `McpManager` / `McpServerConfig`：**MCP 服务端/客户端**（一阶段核心接口）

二阶段需补的 Python 绑定（记录，不阻塞一阶段）：
- 多源 `KnowledgeRegistry`（联邦检索）
- `KnowledgeAccessControl`（作用域/主体/授权/delegation）——二阶段多用户
- `KnowledgeCitationPolicy`（引用强制/溯源）+ `SourceContract`

> 一阶段为「单知识源 + 单用户 + 本地 MCP」，SDK 现有 `McpManager`/`local_source` 足够；二阶段云端多用户才需补 Registry + 权限 + citation 的 Python 绑定。

## 七、迁移到云端（二阶段前置设计）

- 一阶段产出的「知识库核心」（原始层 + 关联层 + 入库管线 + 检索）与 MCP API / 管理后台解耦。
- 二阶段：知识库核心迁到云端服务，团队 coding agent 经 **MCP** 访问，按权限读写（调 MCP 方式不变）。
- MCP 客户端/服务端已就绪（`McpManager`）；需补「知识服务端」的 Registry + 权限 + citation 校验的 Python 绑定。

## 八、风险与注意

1. **GPL 许可**：MinerU 是 GPL-3.0。必须进程隔离调用（CLI/HTTP），不链接进代码库，不污染底座。
2. **图片按需理解**：图片不预嵌入，使用时送多模态——需保证使用时多模态模型可用；离线场景需本地视觉模型。
3. **关联层数据一致性**：关联层可重建，写回需审计留痕（heartbeat 的增量记录）。
4. **归纳知识页准确性**：带 human-on-the-loop，防止 agent 自信地给出错误结论（HoloLithoSim 报告 4.5/7 节教训）。
5. **知识税消除的有效性**：skill 要「薄」（一文闭合、只放不变量），深内容下沉 wiki 按需读，避免撑爆上下文。
6. **MCP 写回安全**：upsert 权限需治理——一阶段单用户可放开，但写回需留审计，为二阶段多用户权限（KnowledgeAccessControl）预留。
